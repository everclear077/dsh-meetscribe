# dsh-meetscribe Word 会议纪要规范

更新日期：2026-11-21
状态：v0.1 模板规范，核心模板已实现并完成 Word 渲染检查

> 验证范围：示例已在 Microsoft Word 中打开并渲染检查；WPS 和 LibreOffice 的兼容性仍是目标，不在本次实测结论内。

## 1. 输出目标

会议结束后直接生成原生 `.docx` 文件，满足：

- 内容正式、简洁、自然；
- 基本信息完整；
- 决议、任务和未决问题清晰；
- 不编造缺失信息；
- 排版美观、克制，适合直接内部流转；
- Microsoft Word、WPS 和 LibreOffice 可正常打开；
- 不将 Markdown 作为用户交付格式。

## 2. 默认模板

第一阶段实现“通用正式会议纪要”。后续可增加项目会议、周会、客户会议和公文风格模板。

### 2.1 标题

使用“会议名称 + 会议纪要”，例如：

产品周会会议纪要

标题居中，不添加装饰性图标、表情或夸张色块。

### 2.2 基本信息表

默认字段：

| 字段 | 要求 |
| --- | --- |
| 会议名称 | 从会议元数据读取 |
| 会议主题 | 用户填写；也可由模型归纳后由用户确认 |
| 会议日期 | 自动生成 |
| 会议时间 | 开始时间—结束时间 |
| 会议地点 | 用户填写，缺失时“待补充” |
| 会议形式 | 线下、线上或混合 |
| 主持人 | 用户指定，缺失时“待补充” |
| 记录人 | 用户指定，缺失时“待补充” |
| 参会人员 | 与已确认的说话人和手工名单合并 |
| 缺席人员 | 用户填写，无信息时“待补充” |
| 关联项目 | 可选 |
| 保密级别 | 可选 |

基本信息优先使用紧凑的两列或四列表格，避免占据过多首页空间。

## 3. 正文章节

默认顺序：

1. 会议议题
2. 讨论主要内容
3. 会议决定事项
4. 任务分工及完成时限
5. 尚未解决的问题
6. 下次会议安排
7. 其他事项

规则：

- 没有内容的可选章节不生成；
- “会议议题”和“讨论主要内容”避免重复；
- 决议只包含已经形成结论的事项；
- 讨论建议、待验证事项不能写成决议；
- 分歧意见需要保留；
- 下次会议没有明确安排时删除该章节；
- 不为凑足结构生成空话。

## 4. 任务分工表

默认列：

| 序号 | 工作事项 | 负责人 | 协同人 | 完成时限 | 备注 |
| --- | --- | --- | --- | --- | --- |

要求：

- 工作事项描述具体、可核对；
- 负责人未明确时写“待确认”；
- 协同人没有依据时留空或使用“—”；
- 截止时间未明确时写“待确认”；
- 不把相对日期擅自转换成不存在的确定日期；
- 逐字稿明确给出日期语境时可规范化，但保留来源；
- 同一任务在多次讨论中出现时合并，保留最终有效结论；
- 存在冲突时列入未决问题，不任意选择一种说法。

## 5. 写作风格与去 AI 味

### 5.1 推荐风格

- 直接记录事实、意见、结论和行动；
- 句子长短自然，避免每段使用相同句式；
- 适度使用“某某提出”“会议确认”“会议决定”“待进一步核实”；
- 只在说话人归属明确时进行具名归因；
- 重要数字、日期和名称与逐字稿一致；
- 保留必要细节，删除重复口语，不压缩掉约束条件。

### 5.2 禁止或重点检查的套话

- 本次会议取得了丰硕成果；
- 在热烈友好的氛围中；
- 与会人员畅所欲言、各抒己见；
- 综上所述、总体而言、值得注意的是等高频连接语；
- 赋能、抓手、闭环、深度融合等无实际信息量的词；
- 为后续工作奠定了坚实基础；
- 大家一致表示，除非逐字稿确实明确记录；
- 作为 AI、根据提供的文本等模型身份描述。

后处理检查用于发现模板化表达，不能机械替换导致语义变化。

## 6. 版式规范

### 6.1 页面

- A4 纵向；
- 统一页边距；
- 页眉可配置会议名称或单位名称；
- 页脚居中页码；
- 短会议不添加单独封面；
- 不制造无意义空白页。

### 6.2 字体与段落

- 标题使用清晰的中文黑体类字体；
- 正文使用适合中文阅读的宋体类字体；
- 一级标题使用统一字号和深色；
- 正文采用舒适字号和行距；
- 标题设置段前、段后间距及与下段同页；
- 正文避免大段居中；
- 列表使用 Word 编号定义，不直接插入圆点字符；
- 每级标题都显式定义字体、字号和段落间距。

具体字号、字体和颜色通过第一份 Word 样张确认后固化为设计令牌。

### 6.3 表格

- 表格总宽度与页面正文宽度一致；
- 同时设置表格列宽和单元格宽度；
- 表头使用浅色底纹和适度加粗；
- 跨页重复表头；
- 避免单行跨页造成阅读困难；
- 任务描述列宽大于序号和负责人列；
- 不使用表格模拟水平分隔线；
- 不使用纯黑底纹或夸张渐变。

## 7. 结构化数据

大模型输出应映射到固定数据结构，而不是直接输出排版文本：

```text
MeetingInfo
Topic[]
DiscussionItem[]
Decision[]
ActionItem[]
OpenIssue[]
NextMeeting?
AdditionalNote[]
```

每个讨论、决议、任务和未决问题可以关联来源 segmentId，用于内部核查。

规则：

- 未掌握的信息使用明确的空值或待确认状态；
- 来源不明确时降低归因确定性；
- 人工编辑的元数据优先于模型推断；
- 原始逐字稿不被结构化结果覆盖；
- 正式 Word 默认不显示 segmentId。

## 8. 长会议处理

1. 按时间和议题对逐字稿分块；
2. 每块提取讨论、决议、任务和未决问题；
3. 合并各块结果；
4. 根据最终发言修正先前临时结论；
5. 对重复任务去重；
6. 保留不同意见和未解决冲突；
7. 最后生成全文摘要和议题结构。

分块失败时保留中间结果并允许续跑，不覆盖上一版有效纪要。

## 9. 技术实现

- 使用 `docx` npm 库直接生成新文档；
- 样式、编号、表格和页面设置由代码统一管理；
- 不使用 Markdown 转 Word 作为最终实现；
- 不以大模型输出控制底层 Word XML；
- 自定义现有 `.docx` 模板属于后续能力，届时采用解包和 XML 编辑，而不是 docx-js 读取旧文档；
- 重新生成时使用新文件名或版本号，不静默覆盖旧文件。

## 10. 文档验证

每次模板变更至少执行：

1. 检查 DOCX ZIP 和 XML 结构；
2. 检查必需样式、编号和页面设置；
3. 使用 LibreOffice 转换为 PDF；
4. 将 PDF 页面渲染为图片并逐页查看；
5. 检查字体替换、表格溢出、分页和页码；
6. 使用 Microsoft Word 和 WPS 做实际打开验证；
7. 验证短会议、长会议、长姓名、长任务描述和无待办等边界样例。

## 11. 默认文件命名

推荐：

```text
会议名称_YYYYMMDD_HHmm_会议纪要_v1.docx
```

文件名需要清理 Windows 非法字符。重新生成递增版本号，保存目录由用户配置。

## 12. 第一份样张验收内容

样张至少包含：

- 完整基本信息表；
- 两个会议议题；
- 三段讨论内容；
- 两条明确决议；
- 三项任务，其中一项负责人或日期待确认；
- 一条未决问题；
- 两页以上分页场景；
- 一页任务表跨页场景；
- 无套话、无编造、无 Markdown 标记残留。

# dsh-meetscribe Word 会议纪要规范

更新日期：2026-11-22
状态：内置正式模板与自定义 `.docx` 模板合并已实现

> 验证范围：当前合成样张已由 Microsoft Word 后台导出为 4 页 PDF，并逐页渲染检查。WPS、LibreOffice 和重启后的 DSH 桌面内置预览不在本次已通过范围内。

## 1. 输出目标

会议结束后生成原生 `.docx`，而不是把 Markdown 改后缀或交给模型直接控制 Word XML。输出应满足：

- 内容准确、简洁，保留决议依据、限制条件和未核实分歧；
- 基本信息、议题、讨论、议定事项、责任人与期限清晰；
- 未提供的信息明确标为“待补充”或“待确认”；
- 版式克制，适合内部流转和人工审核；
- 每次重新生成保留独立版本，不静默覆盖旧文件。

默认模板设计参考了正式纪要写作规范，而不是凭空拼接“AI 总结”版式：

- [University of Manchester：Minutes and actions](https://www.staffnet.manchester.ac.uk/governance/handbook/minutes-actions/)：准确、客观、简洁；记录决议、建议、依据与必要背景；行动项写明责任人、交付内容和时限。
- [University of York：Servicing meetings](https://www.york.ac.uk/staff/essentials/admin/servicing-meetings/)：Agenda、Action Log，以及 item / decision / action 的组织方式。
- [东北石油大学：会议纪要写作规范](https://www.nepu.edu.cn/info/1251/10678.htm)：基本情况、正文、出席/缺席信息和逐项议定事项，保留分歧，避免流水账。
- [湖南工学院：会议纪要规范](https://www.hnit.edu.cn/info/1032/75501.htm)：研究事项、汇报要点、决议事项，以及审核和归档要求。

这些来源用于确定内容组织原则；具体字体、表格和页面参数是 MeetScribe 的本地实现，不声称复制某一单位的法定公文格式。

## 2. 内置“正式会议纪要”模板

### 2.1 页面与字体

- A4 纵向，正文宽度 **8732 DXA**；页面上边距 1701、下边距 1417、左右 1587 DXA。
- 黑白灰配色，不使用彩色装饰条、渐变、图标封面或大面积品牌色。
- 标题 22pt，一级标题 14pt，二级标题和正文 12pt；正文固定 28pt 行距。
- 中文正文使用 FangSong，西文正文使用 Times New Roman；中文标题使用 SimHei，西文标题使用 Arial。
- 页眉显示会议名称，页脚居中显示“第 X 页 / 共 Y 页”。
- 结尾保留“整理：记录人　审核确认：________”，提示纪要仍需人工确认。

### 2.2 基本信息

首页直接显示“会议名称 + 会议纪要”，不添加独立封面。信息表字段为：

| 字段 | 缺失值处理 |
| --- | --- |
| 会议名称、会议主题 | 用户元数据优先 |
| 会议日期、会议时间 | 使用已确认的会议时间 |
| 会议地点、会议形式 | 无依据时“待补充” |
| 主持人、记录人 | 无依据时“待补充” |
| 参会人员、缺席人员 | 不根据声音擅自猜测真实身份 |
| 关联项目、保密级别 | 可选，无依据时“待补充” |

### 2.3 正文章节

按以下顺序生成，空的可选章节不占位：

1. **会议议题**：使用真正的 Word 十进制编号，不使用手工圆点字符。
2. **讨论要点**：按议题组织必要事实、依据、例外和分歧，不写逐人发言流水账。
3. **议定事项**：逐项写明决定、条件和限制；建议或待验证事项不得写成决议。
4. **任务分工**：只有逐字稿有依据时才生成任务。
5. **待核实事项**：保留尚未解决的问题、样本不足或信息冲突。
6. **下次会议安排**：没有明确安排时省略。

`keyPoints` 只能补充讨论正文没有表达的新增约束、例外或依据，不能换句话重复正文。提示词同时禁止“会议取得丰硕成果”“在热烈友好的氛围中”“为后续工作奠定坚实基础”等套话，以及每项机械重复同一句式。

### 2.4 任务分工表

默认六列：

| 序号 | 工作事项及交付要求 | 负责人 | 协同人 | 完成时限 | 状态 |
| --- | --- | --- | --- | --- | --- |

- 工作事项必须具体、可核对；逐字稿明确给出的验收或协作要求在同一单元格中显示为“交付说明”。
- 负责人或期限未明确时写“待确认”，无协同人时用“—”。
- 不把相对日期擅自转换成没有依据的确定日期。
- 表格和单元格同时设置 DXA 宽度，任务列明显宽于其他列。
- 表头跨页重复，避免单行跨页；样张已覆盖 10 项任务和三页连续任务表。

## 3. 自定义 Word 模板

在 **MeetScribe → 识别设置 → 会议纪要模板** 中可以上传 `.docx`、查看模板列表、设为默认或删除用户模板。模板保存在：

```text
%LOCALAPPDATA%\dsh-meetscribe\templates\
```

上传不会自动把模板发送给模型，也不会修改已有 Word。删除当前默认模板后，新任务回退到内置模板。

### 3.1 必需正文标记

模板正文必须且只能有一个独立段落：

```text
{{MEETSCRIBE_BODY}}
```

该段落会被完整替换为生成的议题、讨论、议定事项、任务分工等待整理正文。标记可以被 Word 拆成多个 runs，上传校验和替换会按整段文字识别。缺失、重复或与其他正文混在同一段的标记都会被拒绝。

### 3.2 元数据标记

以下标记可用于正文、页眉和页脚：

```text
{{MEETING_NAME}}
{{MEETING_TOPIC}}
{{MEETING_DATE}}
{{MEETING_TIME}}
{{MEETING_LOCATION}}
{{MEETING_FORMAT}}
{{MEETING_HOST}}
{{MEETING_RECORDER}}
{{MEETING_ATTENDEES}}
{{MEETING_ABSENTEES}}
{{MEETING_PROJECT}}
{{MEETING_CONFIDENTIALITY}}
```

无值的元数据标记替换为“待补充”。含标记的段落保留段落属性，但文字会重组为一个普通文本 run；不要把需要保留的复杂超链接、域或多个不同字符样式与标记放在同一段。

### 3.3 样式与编号合并

- 保留模板自己的页面设置、页眉和页脚。
- 插入正文使用 `MeetScribeTitle`、`MeetScribeHeading1`、`MeetScribeHeading2`，避免覆盖模板已有 `Title`、`Heading1` 等样式。
- 模板已有普通正文和表格样式继续有效；内置正文所需样式会合并进去。
- 生成内容的 `numId` 与 `abstractNumId` 会重新映射，避免与模板已有编号冲突。
- 不重复插入内置首页标题和基本信息表；这些内容由用户通过标记自行安排。

## 4. 不可变任务快照

新任务在模型请求之前读取并重新校验所选模板字节，形成本次任务自己的快照：

```text
点击“生成纪要”
  → 固定模板字节与纪要模型设置
  → 请求模型并校验结构化结果
  → 合并模板并写入新版本 DOCX
```

因此，任务开始后切换默认模板、删除模板或删除已上传文件，不会改变该任务使用的模板。上传模板本身只保存设置和字节；只有这条生成链路真正把模板用于新 Word。

## 5. 不可信模板安全边界

用户模板始终按不可信 ZIP/XML 数据处理，不执行其中任何内容，也不解压到可执行目录：

- 文件最大 **10 MB**，ZIP 最多 512 个条目，解压总量最多 64 MB。
- 拒绝加密、ZIP64、非常规压缩、绝对路径、盘符、反斜杠、`.`、`..` 和目录穿越。
- 拒绝宏、ActiveX、OLE/embeddings、externalLinks、customXml 和可执行文件。
- 校验包内所有 `.xml` / `.rels` 部件，拒绝 DOCTYPE、ENTITY、altChunk、object、control、subDoc、外部 Relationship、DDE 和 INCLUDETEXT 等内容。
- 只在内存中解包、替换和重打包；存储文件名使用插件生成的 UUID，不使用用户提供的路径。

这些限制意味着部分含链接图片、嵌入对象、宏或动态字段的企业模板不能直接上传；需要先另存为不含上述内容的普通 `.docx`。

## 6. 结构化数据与事实约束

模型输出映射到固定的 `MeetingMinutes` 结构：元数据、议题、讨论、决议、任务、待核实事项和可选下次会议。讨论、决议、任务和未决问题可以带来源 `segmentId`，用于内部核查；正式 Word 默认不显示这些 ID。

- 人工元数据优先于模型推断。
- 原始逐字稿不被结构化结果覆盖。
- 不虚构参会人、负责人、期限、地点、决议或交付要求。
- 来源校验和 schema 校验不能证明模型归纳完全忠实，生成后仍需人工复核。

## 7. 验证清单

每次模板变更至少执行：

1. `npm run verify`：TypeScript、DOCX ZIP/XML、样式、编号、页面设置、模板合并与安全拒绝测试。
2. `npm run sample:word`：只使用明确标记的合成内容生成 DOCX/JSON。
3. 将 DOCX 转成 PDF，逐页查看字体替换、分页、表格宽度、重复表头、页码和“待确认”显示。
4. 覆盖短会议、无待办、长姓名、长任务描述、跨页表格、损坏 DOCX、重复/缺失正文标记和外部关系。
5. 在真实 DSH 中分别验证 Office 转换成功、缺少组件、文件变化和 PDF 弹窗关闭；组件 mock 通过不等于真实桌面通过。

当前完整样张为 `docs/samples/meeting-minutes-sample.docx`，包含 2 个议题、3 段讨论、2 项决议、10 项任务、1 项待核实事项和下次会议安排。样张标题明确标记“【合成示例】”，不包含真实会议文本。
